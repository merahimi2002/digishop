# احراز هویت و دسترسی

وضعیت: Better Auth در R01 انتخاب شد؛ نصب، adapter Prisma و مسیرهای اجرایی در R04 ساخته می‌شوند. credentials و اتصال Prisma در مستندات رسمی بررسی شدند. ورود اولیه ایمیل و رمز اختصاصی حساب است. Gmail صرفاً آدرس ایمیل است؛ Google OAuth فعال نیست. رمز مشترک عمومی در تولید ممنوع است. `BETTER_AUTH_SECRET` متغیر secret است؛ انتخاب کتابخانه به معنی ورود فعال نیست.

## چرخه حساب

ثبت‌نام → حساب ایمیل تأییدنشده → تأیید با توکن یک‌بارمصرف دارای انقضا → حساب تأییدشده. ورود، خروج، خروج از سایر نشست‌ها و بازیابی رمز باید طراحی شوند. وضعیت حساب قفل/غیرفعال از وضعیت تأیید ایمیل جدا باشد.

رمز با الگوریتم استاندارد کتابخانه معتبر هش شود. password manager، paste و autocomplete درست پشتیبانی شوند. تغییر یا بازیابی رمز نشست‌های لازم را باطل کند. توکن تأیید/بازیابی در دیتابیس به شکل هش‌شده، محدود به هدف، دارای انقضا و یک‌بارمصرف باشد.

بازیابی و تأیید به ایمیل تراکنشی نیاز دارند؛ تا اتصال واقعی در تولید ادعای ارسال نشود. نرخ ورود و ارسال، پاسخ عمومی برای جلوگیری از account enumeration و سقف تلاش کنترل شود. logging فاقد رمز/توکن باشد.

## نشست و مجوز

session قابل ابطال، کوکی HttpOnly و Secure تولید، SameSite مناسب و محافظت CSRF؛ زمان انقضای idle/absolute هنگام پیاده‌سازی مشخص و تست شود. callback درگاه نباید برای درستی مالی به کوکی مرورگر متکی باشد.

| نقش پیشنهادی | حدود اختیار |
| --- | --- |
| مشتری | پروفایل، آدرس و سفارش خود |
| مدیر محتوا/کاتالوگ | محصول و ترجمه؛ بدون دسترسی به secrets یا تسویه |
| مدیر سفارش | سفارش و ارسال در حدود permission |
| مالک | مدیریت نقش و تنظیمات حساس |

نقش‌ها پیشنهاد ساختاری‌اند؛ نقش پیش‌فرض ثبت‌نام فقط مشتری است. UI مجوز امنیتی محسوب نمی‌شود. هر Server Action، endpoint و ابزار AI مجوز و مالکیت را در سرور بررسی کند. bootstrap مالک فقط با فرمان/مسیر امن و بدون credential ثابت در مخزن؛ تغییر نقش audit شود. برای عملیات بسیار حساس احراز مجدد در نظر گرفته شود.

## OTP آینده

شماره با قالب واحد نرمال شود؛ کد تصادفی امن، هش‌شده، دارای انقضا، حداکثر تلاش و cooldown. شماره به user ID پایدار متصل شود. اتصال حساب ایمیل و موبایل نیازمند اثبات مالکیت است؛ شباهت اطلاعات یا پیام AI مجوز ادغام حساب نیست. اتصال پیامک و تصمیم‌های بازیابی قبل از فعال شدن بررسی شوند.



## پیش‌نیاز داده R03

User/Session/Account/Verification/Address اکنون در schema و migration هستند؛ ورود، bootstrap مالک و adapter Better Auth هنوز اجرایی نیستند و AUTH_ENABLED=false باقی است. هیچ admin یا password پیش‌فرض seed نشده. roleها enumهای CUSTOMER/ADMIN/OWNER هستند؛ R04 باید mapping و permission را صریح پیاده کند. Verification.value به hash hex ۶۴ کاراکتری محدود شده؛ ذخیره/lookup پیش‌فرض adapter بدون بررسی کافی نیست و R04 باید flow token را با این قرارداد هماهنگ کند. credential/OAuth tokenها نباید بدون حفاظت مناسب و مجوز در فیلدهای nullable آینده ذخیره شوند. OI-13/14 هنگام اتصال واقعی لازم می‌شوند.
